# Обоснования конфигурации инфраструктуры (IaC)

## 1. Введение и цели

### 1.1 Назначение документа

Документ описывает и обосновывает выбор конфигурации инфраструктуры для компании «Будущее 2.0» при переходе в облачную среду. Основной фокус — использование подхода Infrastructure as Code (IaC) с применением Terraform для обеспечения воспроизводимости, масштабируемости и безопасности.

### 1.2 Бизнес-цели, определяющие конфигурацию

1. Соответствие регуляторам: Медицинские и финансовые данные требуют изоляции и контроля доступа.
2. Независимость доменов: "Клиники", "Финтех", ИИ, "Фарма", "Электроника" должны развиваться без конфликтов за ресурсы.
3. Отказоустойчивость: Критичные сервисы (запись к врачу, платежи) должны переживать сбои зон доступности.
4. Масштабируемость: Нагрузка на ИИ-сервисы (обработка снимков) может расти скачкообразно.

## 2. Обоснование выбора подхода Infrastructure as Code (IaC)

### 2.1 Почему декларативный подход (Terraform)?

|Критерий|Декларативный подход (Terraform)|Императивный подход (скрипты)|Обоснование выбора|
|-|-|-|-|
|Управление состоянием|Хранит состояние (state), знает, что уже создано|Каждый запуск пытается создать заново или требует сложных проверок|Terraform позволяет безопасно добавлять ресурсы, не трогая существующие|
|Воспроизводимость|Один и тот же код создаёт идентичные окружения (dev/stage/prod)|Скрипты могут давать разный результат из-за неучтённых условий|Критично для тестирования изменений перед выкаткой в прод|
|Контроль версий|Конфигурация — это код, хранится в Git, проходит code review|Скрипты тоже могут храниться в Git, но сложнее отследить изменения в ресурсах|Обеспечивает прозрачность и аудит всех изменений инфраструктуры|
|Удаление ресурсов|Понятно, что будет удалено при применении (plan)|Риск оставить «мусор» или удалить лишнее|Снижает затраты на неиспользуемые ресурсы|

### 2.2 Как IaC обеспечивает воспроизводимость и масштабирование

Воспроизводимость:

* Dev/Test/Prod идентичны: Благодаря Terraform-модулям мы создаём среду разработки, повторяющую продуктивную, но с меньшими размерами VM. Это позволяет ловить ошибки до прода.
* Disaster Recovery: При сбое целого региона мы можем развернуть всю инфраструктуру заново за считанные часы, применив тот же код в другом регионе.

Масштабируемость:

* Модульность: Каждый домен описывается отдельным модулем. Добавление нового домена ("Фарма") — это вызов готового модуля с новыми параметрами.
* Параметризация: Размеры ресурсов задаются переменными. При росте нагрузки мы меняем одну цифру в коде, а не пересоздаём всё вручную.
* Автомасштабирование: Для AKS и некоторых VM мы настраиваем автоматическое добавление нод при росте нагрузки (это также описывается в коде).

## 3. Обоснование выбора ресурсов и их параметров

### 3.1 Сетевая инфраструктура (Hub-Spoke модель)

|Компонент|Выбранное решение|Обоснование|
|-|-|-|
|Hub VNet|Создаётся вручную, с диапазоном адресов 10.0.0.0/16|Центральный узел для связи с on-prem (клиники, банк) через VPN/ExpressRoute. Единая точка выхода в интернет через NAT Gateway.|
|Spoke VNets (для доменов)|Создаются Terraform, диапазоны /20 на домен|Достаточно для тысяч IP-адресов внутри домена, с запасом на рост. Изоляция доменов друг от друга.|
|Network Security Groups (NSG)|Минимально необходимые правила, запрещён весь входящий трафик по умолчанию|Обеспечение безопасности медицинских и финансовых данных. Доступ разрешён только явно.|
|NAT Gateway|Один NAT Gateway на домен (или общий для некритичных)|Исходящий трафик в интернет (например, для обновлений) идёт через статический IP, что упрощает настройку firewall'ов у партнёров.|

### 3.2 Вычислительные ресурсы (Virtual Machines)

Принципы выбора размеров:

* Используем B-series (burstable) для фоновых задач (мониторинг, билд-агенты), где нагрузка непостоянна.
* Используем D-series (general purpose) для большинства сервисов.
* Используем NC-series / NV-series для ИИ-сервисов с GPU.

|Компонент|Размер VM|vCPU|RAM|Диск|Обоснование|
|-|-|-|-|-|-|
|Билд-агент (CI/CD)|Standard_B2s|2|4 GB|30 GB SSD|Нагрузка только во время сборки, большую часть времени простаивает. Burstable — экономия ~40%|
|Jump Box (bastion)|Standard_B1s|1|1 GB|30 GB SSD|Только для администрирования, низкая нагрузка|
|Legacy-компоненты (временные)|Standard_D4s_v4|4|16 GB|100 GB Premium SSD|Требуется стабильная производительность для старых приложений. Premium SSD для быстрой загрузки|
|Нода AKS (системные)|Standard_D4s_v4|4|16 GB|128 GB|Системные поды (DNS, metrics) не требуют больших дисков, но важна стабильность CPU|
|Нода AKS (приложения)|Стандарт: D8s_v4|8|32 GB|256 GB|Типовые микросервисы. Возможно автомасштабирование пула|
|Нода AKS (ИИ/ML)|Standard_NC6s_v3|6|112 GB|512 GB + GPU|Для инференса моделей на GPU. Тяжёлые диски для хранения моделей и данных|

## 4. Безопасность и сетевые настройки (NAT, FW)

### 4.1 NAT Gateway — зачем и как настроен

Зачем нужен:

1. Статический IP для исходящего трафика: Партнёры (например, банковские системы) могут разрешить доступ только с конкретного IP. NAT Gateway обеспечивает единый исходящий IP для всех ресурсов домена.
2. Безопасность: Исходящий трафик можно направить через Firewall для инспекции (чтобы не было утечек данных).

Конфигурация:

* Отдельный NAT Gateway для домена Финтех (строгие требования к исходящим IP).
* Общий NAT Gateway для доменов Клиники и ИИ (менее критично, экономия).
* NAT Gateway привязан к конкретной зоне доступности, поэтому для отказоустойчивости используем балансировку по нескольким зонам.

### 4.2 Сетевые политики (NSG / Firewall)

|Направление|Политика|Обоснование|
|-|-|-|
|Входящий из интернета|Запрещён весь, кроме строго необходимых портов (80/443 для портала, API)|Минимизация поверхности атаки|
|Между доменами|Запрещён по умолчанию, разрешены только явные правила для обмена данными через шину|Изоляция доменов, чтобы утечка в одном не привела к компрометации всех|
|Доступ к Базам данных|Только с IP билд-агентов и серверов приложений внутри VNet|Никакого прямого доступа из интернета к БД|
|Управление (SSH/RDP)|Только через Bastion (Jump Box), с обязательной MFA|Исключение прямого доступа к VM из интернета|

## 5. Заключение

Предложенная конфигурация обеспечивает:

1. Безопасность: Изоляция доменов, управляемый доступ, шифрование данных.
2. Масштабируемость: Возможность увеличивать ресурсы без перестройки архитектуры.
3. Воспроизводимость: Благодаря Terraform вся инфраструктура описана кодом и хранится в Git.
4. Экономичность: Использование burstable VM для фоновых задач, tiered storage для архивов.
5. Соответствие регуляторам: Изоляция медицинских и финансовых данных, аудит изменений через код.
